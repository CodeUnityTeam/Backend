## Для чего нужен Nginx

Nginx может:

- принимать HTTP- и HTTPS-запросы;
- передавать запросы приложению;
- раздавать статические файлы;
- проксировать запросы к другим сервисам;
- ограничивать размер запросов;
- буферизовать запросы и ответы;
- добавлять HTTP-заголовки;
- возвращать инфраструктурные страницы ошибок;
- скрывать внутренние сервисы от прямого доступа.

Пример архитектуры:

```text
Пользователь
    |
    | HTTPS
    v
Внешний Nginx
    |
    | внутренний HTTP
    v
Контейнерный Nginx
    |
    +-- /api/ -----> Backend
    |
    +-- /static/ --> Статические файлы
    |
    +-- /media/ ---> Файловое хранилище
```

Внешний Nginx обычно отвечает за HTTPS, домен и приём запросов из интернета.

Контейнерный Nginx распределяет запросы между сервисами приложения.

---

## Основные директивы

### `location`

Определяет правила обработки URL:

```nginx
location /api/ {
    proxy_pass http://backend:8000;
}
```

Этот блок применяется к запросам, начинающимся с `/api/`.

### `proxy_pass`

Передаёт запрос другому HTTP-сервису:

```nginx
proxy_pass http://backend:8000;
```

В этом случае Nginx работает как обратный прокси между клиентом и приложением.

### `alias`

Связывает URL с каталогом файловой системы:

```nginx
location /static/ {
    alias /app/static/;
}
```

Запрос:

```text
/static/css/main.css
```

будет соответствовать файлу:

```text
/app/static/css/main.css
```

## Пример внешнего Nginx

```nginx
server {
    listen 443 ssl;
    server_name example.com;

    ssl_certificate /path/to/fullchain.pem;
    ssl_certificate_key /path/to/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;

    client_max_body_size 10M;
    server_tokens off;

    location / {
        proxy_pass http://127.0.0.1:8080;

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

Здесь:

- `listen 443 ssl` включает HTTPS;
- `server_name` указывает домен;
- `ssl_certificate` и `ssl_certificate_key` подключают сертификат;
- `ssl_protocols` ограничивает версии TLS;
- `client_max_body_size` ограничивает размер тела запроса;
- `server_tokens off` скрывает точную версию Nginx;
- `proxy_pass` передаёт запрос следующему сервису.

Директива:

```nginx
ssl_protocols TLSv1.2 TLSv1.3;
```

сама по себе не включает HTTPS. Для HTTPS также нужны `listen 443 ssl`, сертификат и закрытый ключ.

## Безопасность

### Скрытие версии Nginx

По умолчанию Nginx может показывать точную версию в заголовке `Server` и на стандартных страницах ошибок:

```text
Server: nginx/1.24.0
```

Чтобы скрыть номер версии, используется:

```nginx
server_tokens off;
```

После этого клиент обычно увидит:

```text
Server: nginx
```

Скрытие версии уменьшает количество доступной извне технической информации, но не устраняет уязвимости. Nginx и используемые Docker-образы всё равно необходимо регулярно обновлять.

## Пример контейнерного Nginx

```nginx
server {
    listen 80;
    server_name _;

    client_max_body_size 10M;

    location /api/ {
        proxy_pass http://backend:8000;

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location /static/ {
        alias /app/static/;
    }

    location /media/ {
        proxy_pass http://object-storage:9000/;
    }
}
```

API передаётся приложению, статические файлы отдаёт сам Nginx, а media-запросы направляются в файловое хранилище.

## Буферизация

### Что такое буфер

Буфер — временное место, где Nginx хранит данные между клиентом и приложением.

Буферизация нужна, потому что клиент и backend могут передавать данные с разной скоростью.

Данные могут храниться:

- в оперативной памяти;
- во временном файле на диске.

Есть два направления:

```text
Запрос: клиент → Nginx → backend

Ответ:  backend → Nginx → клиент
```

---

### Буферизация запроса

За буферизацию тела запроса перед отправкой в backend отвечает директива:

```nginx
proxy_request_buffering
```

По умолчанию:

```nginx
proxy_request_buffering on;
```

При включённой буферизации Nginx сначала принимает тело запроса, а затем передаёт его backend:

```text
Медленный клиент
       |
       v
Nginx принимает запрос
       |
       v
Backend получает запрос
```

Это уменьшает зависимость backend от скорости клиента.

Если тело запроса не помещается в память, Nginx может записать его во временный файл.

В логах появляется предупреждение:

```text
a client request body is buffered to a temporary file
```

Это не обязательно ошибка. Сообщение означает, что для хранения части запроса использовался диск.

#### Отключение буферизации запроса

```nginx
proxy_request_buffering off;
```

После отключения Nginx передаёт тело запроса backend по мере получения от клиента.

Такой режим может использоваться для специальных потоковых загрузок.

Недостаток: медленный клиент дольше удерживает соединение с backend.

Если запрос проходит через несколько Nginx, отключение буферизации на одном уровне не отключает её на следующем.

---

### Буферизация ответа

За буферизацию ответа от backend отвечает директива:

```nginx
proxy_buffering
```

По умолчанию:

```nginx
proxy_buffering on;
```

При включённой буферизации Nginx может быстро принять ответ приложения, сохранить его в памяти или на диске, а затем передавать клиенту с его скоростью:

```text
Backend быстро отдаёт ответ
          |
          v
Nginx сохраняет данные
          |
          v
Медленный клиент
```

Это позволяет приложению быстрее освободить соединение.

#### Отключение буферизации ответа

```nginx
proxy_buffering off;
```

В этом режиме Nginx передаёт ответ клиенту по мере получения от backend.

Это может понадобиться для:

- Server-Sent Events;
- событий в реальном времени;
- потоковой генерации ответа;
- некоторых видов стриминга.

Пример:

```nginx
location /events/ {
    proxy_buffering off;
    proxy_pass http://backend:8000;
}
```

Для обычного REST API буферизацию обычно оставляют включённой.

---

### Основные директивы буферов

```nginx
client_body_buffer_size;
proxy_buffer_size;
proxy_buffers;
proxy_busy_buffers_size;
proxy_max_temp_file_size;
```

#### `client_body_buffer_size`

Определяет размер буфера памяти для тела клиентского запроса.

Если запрос не помещается в буфер, часть данных может быть записана на диск.

#### `proxy_buffer_size`

Определяет размер буфера для начала ответа backend, включая HTTP-заголовки.

#### `proxy_buffers`

Определяет количество и размер буферов ответа:

```nginx
proxy_buffers 8 16k;
```

В этом примере создаётся восемь буферов по 16 КиБ для одного соединения.

#### `proxy_busy_buffers_size`

Ограничивает объём буферов, которые одновременно участвуют в передаче ответа клиенту.

#### `proxy_max_temp_file_size`

Ограничивает размер временного файла, используемого для буферизации ответа.

---

### Нужно ли увеличивать буферы

Увеличивать буферы «на всякий случай» не нужно.

Слишком маленькие значения приводят к более частой записи на диск.

Слишком большие значения увеличивают расход оперативной памяти на каждое соединение.

Размеры следует менять только при наличии:

- конкретной проблемы;
- соответствующих сообщений в логах;
- большого количества временных файлов;
- слишком крупных заголовков;
- статистики реальных запросов и ответов;
- результатов нагрузочного тестирования.

Для обычного API стандартные значения являются нормальной отправной точкой.

---

## Ограничение размера запроса

```nginx
client_max_body_size 10M;
```

Директива задаёт максимальный размер тела запроса.

При превышении ограничения Nginx возвращает:

```text
413 Request Entity Too Large
```

Если запрос проходит через несколько Nginx, ограничение необходимо согласовать на всех уровнях.

Иначе первый Nginx может принять запрос, который затем будет отклонён следующим.

---

## Проксируемые заголовки

```nginx
proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
```

Они передают приложению:

- исходный домен;
- IP клиента;
- цепочку прокси;
- исходный протокол HTTP или HTTPS.

Это особенно важно, если клиент подключается по HTTPS, а внутри инфраструктуры запрос передаётся по HTTP.

## Проверка и применение конфигурации

Перед применением изменений необходимо проверить конфигурацию:

```bash
sudo nginx -t
```

Успешный результат:

```text
syntax is ok
test is successful
```

После этого конфигурацию можно перечитать без полной остановки Nginx:

```bash
sudo systemctl reload nginx
```

Показать итоговую конфигурацию со всеми подключёнными файлами:

```bash
sudo nginx -T
```

Показать версию, модули и параметры сборки:

```bash
nginx -V
```

Проверить конфигурацию Nginx в Docker:

```bash
docker compose exec nginx nginx -T
```

Посмотреть последние записи в логах:

```bash
docker compose logs --tail 100 nginx
```

## Практические рекомендации

Для обычного REST API оставлять буферизацию включённой:

```nginx
proxy_request_buffering on;
proxy_buffering on;
```

- Использовать `server_tokens off`, но не считать скрытие версии заменой обновлений.
- Не разрешать прямой внешний доступ к backend и другим внутренним сервисам.
- Отключать буферизацию только для отдельных маршрутов, которым действительно нужна потоковая передача.
- Не задавать размеры буферов без измерений.
- Согласовывать `client_max_body_size` на всех уровнях Nginx.
- Следить за свободным местом на диске, если приложение принимает или отдаёт крупные файлы.
- Не публиковать внутренние сервисы и контейнерные порты во внешний интерфейс без необходимости.
