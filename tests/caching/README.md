# Тесты кэширования

Этот каталог содержит модульные и интеграционные тесты фактического контракта
кэширования проекта. Тесты проверяют не только наличие ключей в Redis, но и
корректность данных, которые получают анонимные и авторизованные пользователи
после повторного чтения и инвалидации.

## Что проверяется

- списковые endpoints хранят один упорядоченный список ID для комбинации
  фильтров, а не готовые сериализованные страницы;
- параметры пагинации (`page`, `limit`, `offset`) не меняют ключ списка, а
  фильтры и повторяющиеся query-параметры меняют его;
- персональные списки изолированы по ID пользователя;
- анонимный список проектов не кэшируется;
- публичный список ID вопросов Q&A общий для всех, но `is_liked_by_me`
  вычисляется заново для текущего пользователя;
- `filter=my` в Q&A имеет отдельный ключ для каждого пользователя и отклоняется
  для анонимного запроса до обращения к Redis;
- detail JSON проектов, профилей и вопросов разделён по просматривающему
  пользователю; публичный detail Q&A для анонима использует scope `anonymous`;
- фильтры проектов (`favourites`), Q&A (`my`, `popular`) и порядок результатов
  остаются корректными после изменений данных;
- счётчики лайков и участников инициализируются из БД только при cache miss,
  удаляются при изменении и затем заново заполняются актуальным значением;
- изменения проектов, M2M-связей, откликов, участников, избранного, лайков,
  профилей, Q&A и справочников инвалидируют зависимые ключи после commit;
- удаление участника не оставляет в detail-кэше закрытые поля проекта;
- endpoints без кэширования (`profile/me`, отзывы) не начинают случайно читать
  или записывать Redis; изменяющие запросы проверяются как источник инвалидации,
  а не как источник кэшированных ответов.

## Состав набора

| Файл | Назначение |
|---|---|
| `test_cache_keys.py` | Формат ключей, пагинация, фильтры, repeated params и user scope |
| `test_project_list_cache_key.py` | Контракт ключа списка проектов |
| `test_cache_layers.py` | Cache hit/miss для списков, detail JSON и счётчиков |
| `test_invalidation.py` | Матрица зависимостей моделей и ключей, `transaction.on_commit()` |
| `test_qna_anonymous_cache.py` | Анонимный и персональный scope Q&A |
| `test_reference_and_no_cache.py` | Справочники и endpoints без кэша |
| `test_cache_api_integration.py` | Сквозные API-сценарии персонализации, фильтров и инвалидации |

## Запуск

Только тесты кэширования:

```powershell
uv run pytest tests/caching -q
```

Весь набор проекта:

```powershell
uv run pytest -q
```

Дополнительные проверки затронутого кода:

```powershell
uv run python manage.py check
uv run ruff check core projects qna users help feedback tests/caching
```

В `pyproject.toml` для pytest указан `config.settings_test`. Эти настройки через
Testcontainers поднимают изолированные PostgreSQL и Redis, поэтому должен быть
запущен Docker Engine. Запускать `docker-compose.local.yaml` специально для
тестов не требуется. Autouse fixture очищает тестовый Redis до и после каждого
теста.

## Ограничения

Сигнальная инвалидация срабатывает при `save()`, `delete()` и изменениях M2M.
Прямые SQL-запросы и произвольный `QuerySet.update()` обходят сигналы Django.
Если такой способ записи добавляется в код, он должен явно инвалидировать все
зависимые ключи через `transaction.on_commit()` и получить отдельный тест.
